# Mini 3 trial: discovery works; audio handoff needs work

This report contains no account keys, session files, device identifiers, or
private network addresses. The trial used the official Spotify Soloist ARM64
build `1.3.10.25` on a rooted Yandex Station Mini 3. The Quasar bridge and
autostart were disabled throughout.

| Check | Observation |
| --- | --- |
| Official Soloist startup | The binary requires the bundled AArch64 ELF loader. Direct execution failed because `/lib/ld-linux-aarch64.so.1` is absent. Running through `lib64/ld-linux-aarch64.so.1 --library-path lib64` worked. |
| First Spotify Connect pairing | Worked. A track played audibly on the Mini 3. |
| Native Yandex Music | Worked after Soloist was stopped. |
| Spotify after Yandex Music | Soloist reported an active, advancing track, but the speaker was silent. Stopping Yandex Music by voice and restarting Soloist did not restore sound. |
| Remote control | After pairing, the device appeared in Spotify Connect over mobile data. Playback control reached the station, but this test occurred after the audio handoff failure, so remote audio is not yet verified. |
| Quasar bridge | Not installed or enabled. No voice interception was tested. |
| Rollback | Completed: Soloist directory and temporary files removed; no init script; root filesystem read-only; pre-existing Quasar/SSH/OTA files matched their pre-trial hashes. |

## Discovery and Aruba configuration

The dedicated SSID initially used `broadcast-filter arp`, which suppresses
multicast, and AirGroup Guest Multicast was disabled. After setting the SSID's
filter to `disabled` (`show network` reports `none`) and enabling guest
multicast, a PC on the SSID received Spotify DNS-SD responses from the Mini 3.
The phone then discovered and paired the device. These Aruba settings remained
enabled after the device trial. To restore the previous settings:

```text
configure terminal
wlan ssid-profile Polaris-alice
broadcast-filter arp
exit
airgroup
no enable-guest-multicast
end
commit apply
```

Review the live Aruba configuration before applying any rollback; the guest
multicast setting may also affect other services on that guest VLAN.

## Audio finding and next step

During the silent Spotify playback, `/proc/asound/card0/pcm0p/sub0/status`
reported a prepared PCM stream while the stock Quasar `mediad` process held
the playback device. This is evidence of an audio ownership conflict, but it
does not by itself identify the exact control message needed to release it.
The next implementation should coordinate audio focus with Quasar and retain
normal Yandex Music behavior. Do not kill `mediad` or enable the existing
broad voice/cancel bridge as a workaround.

Upstream v1.2.0 has partial coordination: `soloist-bridge.c` sends Quasar
pause/cancel directives in voice and touch handlers, and
`scripts/request_state.sh` waits 0.3 seconds when those handlers initiate
Spotify playback. The WebSocket playback-status handler only records the
Spotify state. It does not hand off audio when playback starts from the
Spotify Connect app, so it does not cover the silent remote-control case
observed here. The bridge has not been validated on this Mini 3.

The first trial's pre-install file backup and the paired Soloist data backup
are stored locally in the Git-ignored `backups/` directory. They are not raw
flash images. The paired data backup contains private Spotify session state.
